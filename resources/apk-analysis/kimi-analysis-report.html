Syntax Highlighting: Prism4j (Pure JVM)

Key Finding: Kimi uses Prism4j — a pure Java/JVM port of PrismJS — for client-side syntax tokenization. No JavaScript engine, no WebView, no bridge overhead. This is the ONLY app in the entire analysis with this approach.

Prism4j is written by noties (Dimitry Ivanov), the same author as the Markwon markdown library. It provides a pure Java implementation of PrismJS grammars, running directly in the Android Dalvik/ART runtime with zero native library or JS engine dependencies.

Rendering: Native SpannableStringBuilder

Key Insights

1. Closest Architecture to android-compose-highlight

Among all analyzed apps (ChatGPT, Claude, GitHub, Gemini, Perplexity, Le Chat, Replit, Kimi), Kimi's approach is the most directly comparable to what android-compose-highlight aims to achieve:

  • Pure JVM tokenization — Prism4j runs in the same process, no IPC or bridge
  • Native span rendering — SpannableStringBuilder is the lowest-overhead path
  • Compose UI layer — Final rendering in Jetpack Compose composables
  • No WebView for code — WebView reserved only for content that requires it

2. Prism4j as a Proven JVM Tokenizer

Kimi's use of Prism4j validates the approach of running a JVM-based tokenizer for mobile code highlighting. Prism4j supports numerous languages via its grammar system and has been battle-tested through its integration with Markwon (a widely-used Android markdown library). The grammar loading is lazy via GrammarLocator, meaning only requested languages are loaded into memory.

3. Compose Multiplatform Shared Code

The presence of assets/composeResources/kimi.shared.generated.resources/ confirms Kimi uses Kotlin Multiplatform with Compose Multiplatform. This means the same highlighting approach likely serves both Android and iOS (via Compose Multiplatform for iOS). This validates KMP as a viable platform for building cross-platform code highlighting libraries.

4. Production-Quality Code UX

The ArtifactCodeBlock with loading animations (LoadingBackground, animateSweep) shows that Kimi invests in code block UX beyond basic highlighting — streaming code gets shimmer animations while tokens are being generated, similar to how ChatGPT handles streaming code output.

5. Font Choice: GeistMono

Kimi bundles Vercel's GeistMono font (Regular + Italic variants) for code rendering. This is a modern, high-quality monospace font designed for code readability, released in 2023. The choice to bundle a custom code font (rather than using the system monospace) indicates attention to code rendering quality.

6. Markwon + Prism4j Ecosystem

The Markwon + Prism4j combination is an established open-source solution for native Android markdown+code rendering. Both libraries are by the same author (noties/Dimitry Ivanov), ensuring tight integration. This ecosystem could serve as a reference implementation or inspiration for android-compose-highlight.

Conclusions

Kimi represents the gold standard for native Android syntax highlighting among all analyzed AI chat apps. By using Prism4j (pure JVM tokenization) combined with SpannableStringBuilder rendering and a Compose UI layer, it achieves the most efficient possible architecture: zero WebView overhead, zero JS bridge latency, zero network dependency for code highlighting.

This approach validates the core thesis of the android-compose-highlight library — that pure JVM/Kotlin tokenization with native Compose rendering is not only viable but is already deployed in production by a major AI company (Moonshot AI) serving millions of users.

The key differences from android-compose-highlight's approach are:

  • Kimi uses an existing Java library (Prism4j) rather than a Kotlin-native implementation
  • Kimi renders to SpannableStringBuilder (View system) rather than directly to Compose AnnotatedString
  • Kimi's highlighting is tightly coupled with Markwon's markdown pipeline, whereas android-compose-highlight is a standalone library

These differences represent architectural trade-offs rather than fundamental disagreements about approach. Both converge on the same core insight: JVM-based tokenization + native rendering is the optimal path for Android code highlighting.

Analysis performed on APK extracted via ADB from an emulator. Decoded using apktool. All findings based on static analysis of smali bytecode, bundled assets, and resource files.
